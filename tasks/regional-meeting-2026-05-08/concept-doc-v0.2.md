## 1. Контекст

По итогам встречи 8 мая с Yandex Cloud команда Faun готовит **облачный pilot распознавания видов** на пассивных аудиозаписях (180 ГБ от Романа, Нижнесвирский заповедник + Санкт-Петербург). Это первая ступень партнёрства; задача — собрать рабочий cloud-pipeline под нужды ООПТ и валидировать команду как партнёра по платформе Президентского фонда. Документ описывает скоуп пилота, целевую архитектуру и смету облачных ресурсов на 2 месяца.

## 2. Что есть на рынке

### 2.1 Модели распознавания

| Модель | Что собой представляет | Релевантность для нас |
|---|---|---|
| **BirdNet** (Cornell Lab) | open-source, 6000+ видов птиц, проверена в полевых условиях | основной кандидат на классификатор pilot |
| **Google Perch 2** (2025) | новое поколение моделей Google для биоакустики, embeddings для retrieval | проверим как альтернативу BirdNet — может оказаться точнее на наших данных |
| **YAMNet** (наш v7) | наша собственная модель из исходного Faun (5 классов антропогенных звуков) | используем для non-bird events; в pilot опционально |

Все три — **это модели, а не готовый софт**: у них либо командная строка, либо узкий научный интерфейс, без полного user-facing продукта. Это создаёт нишу для платформенного решения.

### 2.2 Платформенные референсы

- **ecopi LiveApp** (oekofor.de) — комбинация фото+аудиоловушек с координатами и временными метками, управление архивом, события. **Ближайший по форме референс** для того, что мы строим.
- **Rainforest Connection / Guardian nodes** — anti-poaching через edge-инференс + сетевая передача. Полезен как референс для будущей работы с антропогенными звуками.

### 2.3 Источники размеченных данных (fallback)

Если на данных Романа BirdNet/Perch будут работать плохо, переключаемся или дополняем размеченными корпусами:

- **xeno-canto** — крупнейшая открытая библиотека пения птиц, размеченная орнитологами.
- **iNaturalist** — гражданская наука, аудиозаписи с географическими и видовыми метками.
- **eBird** — научный референс для валидации.

### 2.4 Чего на рынке нет

1. **Российской платформы PAM**, готовой к интеграции в платформу ООПТ Президентского фонда природы.
2. Решения, которое **в первую очередь решает мониторинг видов**, и при этом потенциально расширяется на realtime-детекцию антропогенных событий (вторая задача — побочная возможность, не приоритет пилота).

## 3. Пилот с Yandex Cloud

### 3.1 Цель

Доказать, что cloud-pipeline Faun способен принимать сырые WAV-записи с пассивных аудиоловушек и выдавать пользовательски-полезный CSV-отчёт по видам, с управляемой инфраструктурой Yandex Cloud. Получить основу для решения о расширении сотрудничества.

### 3.2 Скоуп пилота

**Входит:**

- Двухстадийный pipeline: обучение собственной модели выделения значимых событий (autoencoder или акустический ViT) + классификация фрагментов одной из публичных моделей (BirdNet / Perch 2 / YAMNet — выбор финализируется внутри пилота).
- Веб-эндпоинт: пользователь подаёт URL **конкретного WAV-файла** + координаты ловушки → получает ссылку на CSV-отчёт.
- CSV-формат: `трек / секунда начала / длительность / вид / вероятность`.
- Хранение сырого аудио, промежуточных артефактов и результатов в Object Storage YC на всё время пилота.
- Базовый дашборд в DataLens — для визуализации результатов.
- Базовое логирование и мониторинг.

**НЕ входит** (явно):

- ❌ Real-time inference (батчевая обработка).
- ❌ Edge-инференс на ловушке.
- ❌ LoRa / УКВ / GSM передача данных.
- ❌ Триангуляция или локализация источника звука.
- ❌ Распознавание антропогенных звуков (бензопила/выстрел/мотор/голос) как приоритет — возможно как побочный результат, без гарантий.
- ❌ Гарантия accuracy на их данных: записи Романа не размечены, валидация в строгом смысле невозможна. Готовим качественный отчёт по результатам, не количественную метрику.
- ❌ Hardware (датчики, питание, передача).
- ❌ Закупка оборудования.

### 3.3 Архитектура pipeline

Двухстадийный подход. Сырое аудио не идёт сразу в классификатор — сначала выделяем значимые временные события через обученную с нуля модель представлений.

```
   ┌──────────────────────────────────────────────────────────────────┐
   │                       Вход в систему                              │
   │   URL конкретного WAV-файла  +  координаты ловушки  +  метаданные │
   └─────────────────────────┬────────────────────────────────────────┘
                             │
                             ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  Этап 0. Препроцессинг                                            │
   │  • Скачивание WAV из источника (Я.Диск / URL) в Object Storage    │
   │  • Разбивка на короткие сэмплы (5–30 секунд)                      │
   │  • Конверсия в спектрограммы (mel/STFT)                           │
   └─────────────────────────┬────────────────────────────────────────┘
                             │
                             ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  Этап 1. Обучение модели представлений (offline, один раз)         │
   │  • Архитектура: autoencoder или акустический ViT (от нуля)         │
   │  • Тренировочный сет: фоновые сегменты из 180 ГБ Романа            │
   │  • Цель: выучить «обычный» фон леса / города                       │
   │  • Среда: Yandex DataSphere + GPU (T4)                            │
   └─────────────────────────┬────────────────────────────────────────┘
                             │
                             ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  Этап 2. Inference модели представлений (на каждый новый файл)    │
   │  • Прогон спектрограмм через AE/ViT                               │
   │  • Выделение онсетов: точки, где модель «не уверена» в фоне       │
   │    (высокая reconstruction loss или attention-spike)              │
   │  • Результат: список временных фрагментов-кандидатов               │
   └─────────────────────────┬────────────────────────────────────────┘
                             │
                             ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  Этап 3. Классификация выделенных фрагментов                       │
   │  • Кандидаты: BirdNet, Perch 2, YAMNet (выбор финализируется      │
   │    в ходе пилота через A/B на сэмпле)                              │
   │  • Каждый фрагмент → метка вида + вероятность                     │
   └─────────────────────────┬────────────────────────────────────────┘
                             │
                             ▼
   ┌──────────────────────────────────────────────────────────────────┐
   │  Этап 4. Агрегация и выдача                                       │
   │  • Сбор результатов в CSV                                          │
   │  • Запись в Object Storage                                         │
   │  • Возврат ссылки пользователю                                     │
   │  • Опционально: визуализация в DataLens по координатам             │
   └──────────────────────────────────────────────────────────────────┘
```

**Почему такая архитектура, а не прямой прогон BirdNet по сырому аудио:**

- Сырые записи леса — это часы тишины + редкие события. Прямой прогон классификатора по всему — расточительно по compute и шумно по результатам.
- Модель представлений учит «нормальный» фон конкретного места записи (Нижнесвирский) — это даёт более чистый сигнал онсетов, чем универсальные методы (RMS, spectral flux).
- На втором этапе классификатор работает только на интересных фрагментах — выше точность, ниже стоимость.
- Если BirdNet окажется неподходящим, классификатор заменяется без перестройки всего pipeline.

### 3.4 Deliverable пилота

К концу 2-месячного пилота заказчик получает:

1. **Работающий веб-эндпоинт** на инфраструктуре Yandex Cloud.
2. **CSV-отчёты** по обработанным файлам Романа в формате выше.
3. **Базовый дашборд в DataLens** — визуализация результатов по координатам и времени.
4. **Документация** по pipeline + handover-инструкция для команды Сергея.
5. **Грубая оценка масштабирования на 10 000 ГБ** (10 ТБ — ориентир объёмов к концу летнего сезона): какие сервисы упрутся, какие узкие места появятся, какой порядок стоимости.
6. **Кодовая база pilot** в git-репозитории.

### 3.5 Сроки

Календарь от старта (день 0 = открытие фолдера YC + получение ссылки от Романа):

| Неделя | Что происходит |
|---|---|
| 1–2 | Setup облака, IAM-роли, terraform, копирование 180 ГБ в Object Storage, базовые скрипты препроцессинга |
| 3–4 | Обучение AE/ViT на фоновых сегментах в DataSphere, итерации архитектуры |
| 5 | Inference AE/ViT по корпусу, выделение онсетов, первая выдача кандидатных фрагментов |
| 6 | A/B классификаторов (BirdNet / Perch 2 / YAMNet) на сэмпле, выбор основного |
| 7 | Веб-эндпоинт + базовый DataLens-дашборд + документация |
| 8 | Финальный прогон всего корпуса, handover, демо с Женей и Сергеем |

**Итого: 2 месяца.** Жёсткого дедлайна нет (Женя 8 мая: «не торопиться»), но критический путь определяется тем, как быстро откроется доступ к облаку и придёт ссылка от Романа.

### 3.6 KPI пилота

Минимальный набор измеримых KPI, чтобы не плодить бессмысленные показатели:

| KPI | Целевое значение |
|---|---|
| Готовность handover | Документация + git-репо + успешный прогон сторонним пользователем на финальном созвоне |
| Соблюдение бюджета облака | В рамках сметы (см. §4), без выхода за верхнюю границу |
| Грубая оценка масштабирования | Описана для горизонта 10 ТБ |

Accuracy в строгом смысле не закладываем как KPI: данные Романа не размечены, валидация требует ручной разметки экспертом, которая выходит за скоуп пилота. Готовим **качественный отчёт**: какие виды распознаны уверенно, где модель сомневается, что мешает.

## 4. Смета облачных ресурсов

### 4.1 Допущения

| Параметр | Значение | Источник / комментарий |
|---|---|---|
| Объём входных данных | 180 ГБ + запас на повторные загрузки | от Романа |
| Часов аудио (оценка) | 200–250 ч | при WAV-стерео-44 кГц это ~120–250 ч, берём с запасом |
| Длительность пилота | 2 месяца | план выше |
| Облако открывает | Сергей / Yandex Cloud | пилот за счёт ресурсов YC |
| AE/ViT обучается с нуля | да | требует серьёзный GPU |
| Сырое аудио хранится весь пилот | да | для повторных прогонов и итераций |

### 4.2 Сервисы Yandex Cloud в пилоте

| Сервис | Роль |
|---|---|
| **Object Storage** | хранение raw WAV, спектрограмм, онсетов, CSV-результатов |
| **Compute Cloud** | VM с pipeline (препроцессинг + inference классификатора), 8–16 vCPU |
| **DataSphere (GPU)** | обучение AE/ViT с нуля + experiment runs (T4) |
| **DataSphere (CPU)** | research notebooks, разметка, эксперименты |
| **Cloud Functions** | submit job + status check за web-формой |
| **API Gateway** | публичный HTTPS-эндпоинт |
| **Managed PostgreSQL** | трекинг submitted jobs, статусов, метаданных файлов |
| **DataLens** | базовый дашборд по результатам и координатам |
| **Cloud Logging** | логи всего pipeline |
| **Cloud Monitoring** | uptime + базовые алерты |
| **Container Registry** | хранение Docker-образов pipeline |

### 4.4 Что не учтено в смете

- **Человеко-часы команды Faun** — на этапе пилота команда работает за свой счёт. Если за пилотом следует фаза с участием Faun как подрядчика — финансирование команды обсуждается отдельно.
- **Лицензии моделей** — BirdNet open-source (CC-BY-NC), Perch 2 — Google research license; для коммерческого использования за пределами пилота нужно отдельное оформление.
- **Hardware и связь** — пилот cloud-only.
- **Разметка данных экспертом-орнитологом** — за скоупом пилота.
